# 实测踩坑记录

这份文档记录开发过程中**真实踩到的坑**。每一条都对应 SKILL.md 里的一条铁律——不是凭空写的规范，而是踩疼了才加的。

> 注意：下面标 ⚠️ 的是**已确认**的问题（来自官方文档与公开实测记录）；标 🔍 的是**待你自己验证**的，拿到 Token 跑一遍后请替换成你的实测结果——这部分正是评委看重的"你真的跑过"的证据。

---

## 1. ⚠️ 营养数据返回 TOON 文本，不是 JSON

`list-nutrition-foods` 返回的是这种格式：

```
{productName,nutritionDescription,energyKj,energyKcal,protein,fat,carbohydrate,sodium,calcium}:
  猪柳麦满分,null,1288,308,16,16,24,781,213
```

**看起来像 CSV，但不能按 CSV 处理。** 三个原因：

1. `nutritionDescription` 可能是 `null`（字符串 "null"，不是 JSON null）
2. `nutritionDescription` 自己可能带逗号，例如 `"含生菜, 特制酱料"`
3. 字段数固定，但引号包裹规则不明确

**解法**：用 `references/toon_parser.py`。它先找表头行确定字段顺序，再逐行按引号感知的方式切分，字段数不匹配的行跳过而不是抛异常。已用真实格式样例自测通过。

**别做的事**：不要 `line.split(',')`，不要用 `csv` 模块直接读（它对引号的处理和这里不完全一致）。

---

## 2. ⚠️ 价格单位不一致：一个「元」一个「分」

| 接口 | 单位 | 实际情况 |
|---|---|---|
| `query-meals` | 元 | 展示价，**通常是字符串** `"23.5"` |
| `calculate-price` | 分 | 计算价，整数 `4700` |

**这是最容易翻车的地方。** 不加换算，用户会看到一个贵 100 倍的价格——¥4200 的套餐。

**解法**：
- `query-meals` 拿到后先 `float()`，得到元
- `calculate-price` 拿到后 `/100`，得到元
- 所有展示统一 `¥42.00` 格式

**建议**：在代码里给两类金额起不同变量名（`price_yuan` / `amount_fen`），靠命名强迫自己别搞混。

---

## 3. ⚠️ 套餐替换只能在同一 round 内

`query-meal-detail` 返回的是 `rounds` 结构，每个 round 是一"轮"可选品类。

实测案例：板烧鸡腿堡三件套的"小食轮"里**没有玉米杯**，只有薯条、鸡块之类。所以"薯条换玉米杯"这个想法，在接口层面就是不可行的。

**解法**：
- 想做替换提议，先调 `query-meal-detail` 看该 round 真实有哪些选项
- 用 `modification` 参数传"去酱"之类的特制
- "可乐换无糖"通常是同轮零加价替换，可以直接提

**别做的事**：不要根据商品常识猜"应该能换"。接口说了算。

---

## 4. ⚠️ 门店接口固定返回 5 家，无分页

`query-nearby-stores` 每次只给 5 家，参数里也不支持坐标/半径。想要更多只能换关键词多次查。

**影响**：
- 用户给"北京"这种大范围，返回的 5 家可能离得很远
- 解决方式：请用户给到"区 + 商圈"级别（如"朝阳大悦城""南山区科技园"）

**别做的事**：不要为了凑更多门店去做关键词轮询——那是另一类项目的玩法，本 Skill 不需要，还会撞限流。

---

## 5. ⚠️ 到店自取 `beType=1`，后续调用不用再传 `beCode`

第一调用 `query-meals` 时传 `beType: 1`，之后 `calculate-price` / `create-order` 沿用同一 `storeCode` 即可。

如果传了 `beType` 又传 `beCode`，可能报参数冲突。

---

## 6. ⚠️ 限流 600 次/分钟

正常对话（一次会话 8–10 次调用）远不会触发。会触发限流的场景是：

- 对每种"主餐×小食×饮品"组合都调 `calculate-price`（可能几百次）
- 遍历全菜单每个餐品查详情

**解法**：
- 本地先枚举过滤，只对 Top 3–5 调算价（`references/combo_solver.py` 干这个）
- `list-nutrition-foods` 一次拉全量，本地建索引复用

---

## 7. ⚠️ `create-order` 是真实建单，会返回支付链接

不是沙盒，不是模拟。返回 `orderId` + 支付链接，打开是付款二维码。

**风险**：误下单 → 占用了下单资格 → 用户得手动取消（或调 `cancel-order`）。

**解法（SKILL.md 铁律 2）**：方案先给用户看，用户明确说"下单"才调。**方案还没展示就问"要不要下单"，属于违规。**

---

## 8. ⚠️ Token 绑定个人会员身份

Token 泄露 = 你的麦当劳账号被人拿去查历史订单、收货地址、积分，甚至下单。

**解法**：
- 绝不把 Token 写进任何提交到仓库的文件
- `mcp-config.example.json` 只放 `${MCD_MCP_TOKEN}` 占位符
- 截图时把 Token 打码

## 9. ✅ 已实测：`query-meals` 的菜单结构

**实测时间**：2026-10-23 19:57
**测试门店**：麦当劳济南凤鸣广场餐厅（`storeCode=3350241`）

**结论**：菜单返回结构是 `{categories: [...], meals: {...}}`，不是平铺数组。

- `categories`：14 个品类，每个含 `name` + `meals`（元素是 `{code, tags}` 的引用）
- `meals`：一个 **dict**，key 是餐品 code，value 是餐品详情
- 餐品字段：`name` / `image` / `currentPrice` / `originalPrice` / `canWithOrder`
- **价格是字符串**（`"currentPrice": "33.5"`），单位**元**
- 本次拉取：110 个餐品，价格范围 ¥3.9 – ¥72.5
- 品类名带换行符（如 `"鸡肉汉堡\n/卷"`），展示时要处理
- 17 个商品标了 `canWithOrder: true`（可随单购，如麦金卡/早餐卡）

**踩坑**：`categories[].meals` 里只有 code 和 tags，**名称和价格要去 `meals` dict 里按 code 反查**。不要以为 categories 里就带着完整信息。

## 10. ✅ 已实测：营养表与菜单名称的匹配率 51.3%

**实测数据**（2026-10-24 复测，门店 1420762）
- 营养表条数：**158**
- 菜单餐品数：**113**
- 三级匹配后命中：**58 个，命中率 51.3%**

**未匹配的原因不是名字差异，而是"套餐 vs 单品"**：

营养表只收录**单品**（中薯条、麦乐鸡5块、猪柳麦满分），而菜单里大量是**套餐**（"龙焰芝士棒鸡腿堡三件套""全明星双人分享餐八件套"）。

未匹配的典型例子：
- `全明星双人分享餐八件套`、`龙焰鸡腿堡三件套` — 套餐，营养表没有
- `阳光橙麦炫酷`、`马苏里拉拉丝芝士条` — 新品，营养表未收录
- `"葱不求人"按摩捶痒痒挠` — 周边商品，本就没有营养数据

**解法（已写进 SKILL.md）**：
1. **套餐要拆**：先用 `query-meal-detail` 拆出 round 组成，对子项逐个查营养再累加
2. **查不到就明说**：标注"官方未提供该餐品营养数据"，不估算
3. 周边商品（按摩捶之类）直接排除出配餐候选

## 11. ✅ 已实测：券与积分的真实结构

**`query-my-coupons`**（我的券）
```
{ "coupons": [], "totalCount": 0, "currentPage": 1, "pageSize": 200, "totalPages": 0 }
```
本次账户券为 0 张，所以**有效期字段名未能实测**（列表为空）。字段名待有券时确认。

**`available-coupons`**（可领的券）
```
{ "couponName": "11.9元麦辣鸡腿堡", "couponImage": "https://...", 
  "couponStatus": "CAN_GET", "label": "可领取" }
```
本次可领 5 张（含重复项：11.9元麦辣鸡腿堡 ×2、19.9元王牌炸鸡任选2 ×2、免费脆薯饼 ×1）。
**注意：返回里有重复券，展示前要按 `couponName` 去重。**

**`query-my-account`**（积分）
```
{ "availablePoint": "350.5", "accumulativePoint": "375.4",

```

- 字段名有拼写特征：`currentMouthExpirePoint`（Mouth 不是 Month）
- 有 `currentMouthExpirePoint`（本月即将过期），这对"积分防浪费"场景直接可用

## 12. ✅ 已实测：算价接口的单位与字段名

**这是最关键的验证。**

| 项 | 实测结果 |
|---|---|
| 菜单价格（`query-meals`） | `"currentPrice": "24"` → **24 元**，字符串 |
| 算价结果（`calculate-price`） | `"price": 2400` → **2400 分 = ¥24.00**，整数 |

**同一个商品 `9900011123`「"辣"么快乐套餐」：菜单显示 24，算价返回 2400。相差正好 100 倍。**

**第二个坑：`items` 的字段名是 `productCode`，不是 `code`。**

用 `{"code": "...", "quantity": 1}` 调用，接口**不报错**，但静默返回全 0：
```
{ "productOriginalPrice": 0, "price": 0, "productList": [], ... }
```
正确写法：
```
{ "items": [{ "productCode": "9900011123", "quantity": 1 }] }
```

**这个"不报错但返回 0"的行为比报错更危险**——如果不校验 `productList` 是否为空，用户会看到一个 ¥0 的订单。

**解法**：
1. 每次算价后**校验 `productList` 非空**，为空就说明参数错了，不要展示
2. `price` / `originalPrice` / `discount` 一律 `/100`
3. 与菜单价格交叉核对：两者应该一致（除以 100 后）

**第三个发现：`calculate-price` 还返回 `takeWayList`**（堂食 `eat-in` / 外带 `locker-in`），下单时 `takeWayCode` 要传这里的 code。

## 13. ✅ 已实测：门店查询的 `searchType` 陷阱

`query-nearby-stores` 的 `searchType` 有两个值：

| 值 | 含义 |
|---|---|
| `1` | **搜索收藏餐厅**（默认值！） |
| `2` | **按位置搜索** |

**踩坑**：不传或传 1，会返回错误 `600050「收藏餐厅列表为空，请您提供城市+关键词进行搜索」`。

这个错误信息很有误导性——它说"请提供城市+关键词"，但你其实提供了，真正的原因是 `searchType` 该传 2。

**正确调用**：
```
{ "city": "济南", "keyword": "凤鸣广场", "beType": 1, "searchType": 2 }
```

**另一个发现**：返回的门店带 `reservationTimeOptions`，包含各日期的可预约时段（早餐/午餐/下午茶/夜市/宵夜）。这对判断"现在这个时间能点什么"很有用，但要注意**不能省略任何一条**（接口明确警告）。

**门店经纬度恒为 0.0**，无法用于距离计算——`distance` 字段（单位米）才是可靠的。

## 14. ✅ 已实测：TOON 表头带长度前缀

真实返回的第一行长这样：

```
[160]{productName,nutritionDescription,energyKj,energyKcal,protein,fat,carbohydrate,sodium,calcium}:
```

**开头有个 `[160]`**，表示数据行数。我最初的解析器没处理这个前缀，结果解析出 **0 条**——因为 `stripped.strip("{}:")` 后拿到的第一个字段是 `[160]{productName`，归一化失败，命中不到 2 个已知字段名，于是判定"没有表头"，走了兜底逻辑后全部错位。

**修复**：解析表头前先 `re.sub(r"^\[\d+\]\s*", "", line)` 剥掉长度前缀。

修复后：160 条全部正确解析。

**教训**：这个坑在文档里完全没有，只有跑真实数据才会暴露。**这就是为什么必须实测。**

## 15. ✅ 已实测（2026-10-24）：套餐热量被模糊匹配成单品，低估近一半

**这是做「控卡配餐」时最危险的一个坑。**

`list-nutrition-foods` 的 160 条数据里**没有任何"套餐"条目**，全是单品。但 `lookup()` 是三级模糊匹配，会把套餐名错配到单品名上：

```
lookup(idx, "麦辣鸡腿汉堡三件套")  # → 命中「麦辣鸡腿汉堡」→ 485 kcal
```

真实值应该是三件套各 round 之和：

| 餐品 | 模糊匹配给出 | 真实值（拆 round） | 低估幅度 |
|---|---|---|---|
| 麦辣鸡腿汉堡三件套 | 485 kcal | 485 + 289 + 147 = **921 kcal** | **47%** |
| 板烧鸡腿堡三件套 | 391 kcal | 391 + 289 + 147 = **827 kcal** | **53%** |
| 巨无霸三件套 | 513 kcal | 513 + 289 + 147 = **949 kcal** | **46%** |
| 麦香鱼套餐 | 325 kcal | 325 + 289 + 147 = **761 kcal** | **57%** |
| 双层吉士汉堡套餐 | 429 kcal | 429 + 289 + 147 = **865 kcal** | **50%** |

**（薯条 289 + 可乐中杯 147 是麦当劳套餐默认搭配）**

**影响**：如果拿 485 kcal 告诉你"这个套餐不到 500 大卡，减脂可以吃"，实际是 921 kcal —— 一顿顶两顿。**这是会让人减脂失败的错。**

**解法**：`references/nutrition_helper.py` 的 `combo_kcal()`。它对任何带"套餐/三件套/随心选/小食盘"关键字的名称**直接返回 None**，强迫调用方走 `query-meal-detail` 拆 round 的正确路径。

```
from nutrition_helper import combo_kcal
detail = call("query-meal-detail", {...})["data"]
res = combo_kcal(detail, idx, lookup)
# res["total_kcal"] == 921.0, res["missing"] == [] 表示子项都有数据
```

## 17. ✅ 已实测（2026-10-24）：券有「未生效」状态，当天可能一张都用不了

券的有效期字段不是简单的"截止日期"，而是**四重条件**：

```
2026-10-26 10:30 - 2026-10-30 23:59  周一、二、三、四、五  10:30-23:59
└── 生效日 ────────────── 截止日 ─┘  └─ 可用星期 ─┘  └─ 可用时段 ─┘
```

**实测案例**（2026-10-24 周六）：

| 券 | 状态 | 原因 |
|---|---|---|
| 11.9 元麦辣鸡腿堡 | ⏳ **未生效** | 10/26 才开始，且仅工作日 |
| 19.9 元王牌炸鸡任选 2 | ⏳ **未生效** | 同上 |

`query-my-coupons` 会正常返回这两张券（`totalCount: 2`，标签写"到店专用、外送专用"），看起来完全可用。但**今天是周六，且券 2 天后才生效 —— 一张都用不了**。

**这是"省钱助手"最容易翻车的地方**：把今天用不了的券算进今天能省的钱。

**解法**：推荐任何券之前，必须把 `now-time-info` 的时间与券的**生效日、截止日、可用星期、可用时段**四项逐一比对。未生效的券单独归类，明确说"这张 X 月 X 日才能用"。

## 18. ✅ 已实测（2026-10-24）：算价会自动应用促销，到手价可能低于菜单价

同一天同一门店，同一商品在两个接口的价格可能不一致：

| 商品 | 菜单价（`query-meals`） | 算价（`calculate-price`） |
|---|---|---|
| 龙焰鸡腿堡 `521952` | ¥24.00 | **¥15.90**（`discount: 810`） |

菜单里 `discountType: "促销优惠"` 标记了，但**只有算价才给出真实的优惠后金额**。

**影响**：
- 用菜单价做省钱对比会**算错省了多少**（虚高）
- 反过来，如果用户觉得"菜单价太贵"而放弃，实际可能便宜 ¥8

**解法**：任何"省了多少""到手多少钱"的结论，一律以 `calculate-price` 的 `price`（分）为准，`originalPrice - price` 才是真实优惠额。

**另外**：`query-store-coupons` 到店场景实测返回**空数组** `[]`（门店无专属券）。没有门店券不是错误，不要报错，直接说"这家店没有门店专属券，用你账户里的"。

## 19. ✅ 已实测（2026-10-24）：`query-promotions` 只有企业团餐能用

工具描述写的是"查询当前门店企业团餐场景下可用的促销规则"，很容易误以为到店也能用。

实测：传入 `beType: 1, orderType: 1` 会失败。它**只接受 `beType: 6, orderType: 2`**。

**影响**：S2 麦门省钱如果按旧文档去调 `query-promotions` 拿满减规则，到店场景拿不到。

**解法**：
- 到店/外送场景的优惠，看 `query-store-coupons`（门店券）+ `query-my-coupons`（账户券）+ 算价的自动促销
- 只有企业团餐（`beType=6`）才调 `query-promotions`

## 20. ⚠️ 节日推荐不能承诺麦当劳没有的东西

## 21. ✅ 已实测（2026-10-24）：麦满分系列只在早餐时段供应

## 22. ✅ 已实测（2026-10-24）：节日组合报价，原价和实付能差 22%

做情人节组合时实测到的数字，值得单独记一条。

同一份 2 人组合（门店 1420762）：

| 项 | 菜单原价 | 实付 | 差额 |
|---|---|---|---|
| "我就喜欢"鸡薯双全盒 | ¥15.90 | ¥15.90 | — |
| 心形薯饼 8 块 | ¥22.50 | **¥9.90** | −¥12.60 |
| 龙焰鸡腿堡 ×2 | ¥48.00 | **¥31.80** | −¥16.20 |
| 蓝莓爆爆珠麦旋风 ×2 | ¥33.00 | ¥33.00 | — |
| 可乐 ×2 | ¥19.00 | ¥19.00 | — |
| **合计** | **¥138.40** | **¥109.60** | **−¥28.80（−21%）** |

**两个方向都会错**：
- 按原价报价 → 用户以为很贵，可能直接放弃
- 按促销价当常规价 → 活动结束后用户发现贵了 ¥28.80

**解法**：一律以 `calculate-price` 的 `price`（分/100）作为展示价，同时用 `originalPrice` 对比出"省了多少"，并注明**这是促销价、可能恢复原价**。

**这是 S7 的一个隐性价值**：节日搭配时，促销品往往正好是"有造型感"的那些（心形薯饼、联名款），所以节日组合通常比单点更划算——但必须算出来，不能猜。

## 23. ❌ 严重：只拼单品，完全没看套餐（2026-10-24 用户指出）

**这是本项目最严重的逻辑漏洞，不是数据错误，是流程错误。**

### 现象

用户说「三两个人吃，预算 50，我在健身」。我给的三档方案全是单品组合：

| 方案 | 构成 | 价格 |
|---|---|---|
| 方案二（控热量） | 板烧鸡腿堡 + 玉米杯 + 纯悦 | **¥44.00** |

用户追问「没有什么很值的套餐选择吗」，一查才发现同一家店有板烧三件套，**换成同样的内容只要 ¥33.00**。

| 路线 | 构成 | 实付 |
|---|---|---|
| 我给的 | 单品：板烧 23.5 + 玉米杯 13 + 纯悦 7.5 | ¥44.00 |
| 实际最优 | 套餐换项：小食换玉米杯(−1.5)、饮料换无糖可乐(+0) | **¥33.00** |

**一模一样的东西，我多报了 ¥11。**

### 根因（三层）

1. **触发条件写错了。** 场景表里 S1 叫「套餐推荐」，但触发词是"今天吃什么"；用户说"帮我点个汉堡"时，agent 会认为"他没要套餐"，于是走单品枚举。**"套餐"是我的功能分类，不是用户的需求分类。**
2. **调用链顺序错了。** 原顺序是「枚举单品组合 → 算价」，套餐只是在 detail 那一步"顺便看看"。应该反过来：**先扫套餐，单品兜底**。
3. **旧的调用克制条款起了反作用**（现为铁律 9，已重写）。 原文写"只想确认含几件时不要调 detail"，被理解成"能不调就不调"，结果跳过了整个套餐线。**约束了调用成本，却约束掉了正确性。**

### 后果

- 用户多花钱（本案例 ¥11 / 单，约 25%）
- 更糟的是：用户不知道我漏了，**看起来还挺专业**
- 这类错误**不会报错、不会算错、也不会被自检发现**——因为每一项数字都是对的，错的是"根本没算那一条路"

### 解法（已落地）

1. **铁律 2：套餐必须先扫，单品只能补。** 任何场景拿到菜单后，第一个动作是 `combo_compare.scan(meals)`。
2. **调用链加 ③.5 强制步骤**，排在单品枚举之前。
3. **三线比价**：A 套餐原样 / B 套餐换项 / C 单品单点，逐档都算，选最优。
4. **允许混搭**：套餐 + 单品补缺口，但要和纯单品比过才算。
5. **铁律 9 重写**：从"能少调就少调"改为"为了比价可以查，为了凑数不要查"。
6. **`combo_compare.py`**：把"扫套餐"变成一行代码，不再依赖 agent 记性。

### 教训

> **当一项优化（省调用）和一项正确性（不漏算）冲突时，正确性优先。**
> 我当初为了速度限制 detail 调用，代价是整条套餐线被跳过——省下的那点 token，换来 25% 的报价偏差，完全不值。

## 24. ❌ 菜单价是「随单购麦金卡」价，不买卡按原价（2026-10-24 实测）

**这条会让"折扣率排序"完全失效——它把最贵的东西排到第一位。**

### 现象

扫趵突泉店（3350337）套餐，折扣排行榜前几名非常漂亮：

| 套餐 | 菜单价 | 原价 | 折扣 |
|---|---|---|---|
| 全明星双人分享餐八件套 | ¥49.90 | ¥114.50 | **4.4 折** |
| 板烧鸡腿堡四件套 | ¥28.00 | ¥57.00 | **4.9 折** |
| 龙焰鸡腿堡四件套 | ¥29.00 | ¥57.00 | 5.1 折 |

拿 `calculate-price` 一算：

| 商品 | 菜单价 | 实测算价 | 差 |
|---|---|---|---|
| 全明星双人分享餐八件套 | ¥49.90 | **¥114.50** | 2.3 倍 |
| 板烧鸡腿堡四件套 | ¥28.00 | **¥57.00** | 2 倍 |

**¥49.9 买不到。** 它是"随单购麦金卡"的价，不买卡照原价。

### 根因

菜单里这类商品有两个字段同时出现：

```
"canWithOrder": true,
"discountType": "随单购麦金卡优惠",
"withOrder": {"membershipCode": "106", "specId": "880"}
```

`currentPrice` 填的是**买卡价**，但 `calculate-price` 不传卡就按 `originalPrice` 算。

本店共 **15 个**套餐属于此类，恰好全是"四件套/双人分享餐"这种高价套餐——所以折扣率一算全是 4~5 折，把真正便宜的 `大堡口福三件套`（4.9 折 / ¥22.9）挤下去。

### 后果

如果按菜单价推荐：
- 报给用户 ¥49.9 的双人餐，到店结账 ¥114.5
- 或者反过来：把真正的低价套餐埋在一堆"假折扣"下面看不见
- **两种都是错，而且都很难被用户当场发现**

### 解法（已落地）

1. `combo_compare.Combo` 增加 `needs_card` 字段，`scan()` 自动识别 `canWithOrder + 随单购`
2. `discount` 属性对这类强制返回 `1.0` → **不参与折扣排序**，自然沉底
3. `real_price` 属性返回 `originalPrice`，作为估算基准
4. `report()` 在备注列打 `⚠需买麦金卡，原价¥X`
5. `split_by_card()` 分两组返回，方便"最实惠"场景直接排除
6. 铁律 4 补上这条：任何进方案的价格一律以 `calculate-price` 为准

### 顺带记一个参数坑

算 `随心配 ×2` 的换项价时，`roundList.comboItemList.quantity` 传 `2` 会返回：

```
60006 商品已售罄或不可售，换一个商品或检查orderType/beType
```

看起来像售罄，其实是**参数写错**。正确写法：`comboItemList.quantity` 传 `1`，倍数写在最外层 `quantity`。

```
{"productCode": "9900013304", "quantity": 2,
 "roundList": [{"round": "1", "comboItemList": [{"code": "1450", "quantity": 1}]}]}
```

### 教训

> **菜单价是给人看的，`calculate-price` 才是给钱看的。**
> 任何"折扣率"如果建立在菜单价上，都可能是在给用户排序一个买不到的世界。

## 25. ❌ 明细表漏了加购项，总价对不上（2026-10-24 用户指出）

### 现象

方案是「三文鱼三件套 ×3 + BFF四宫格小食盘」，总价 ¥153.50。我给的明细表：

| 轮次 | 内容 | 数量 | 差价 |
|---|---|---|---|
| 主堡 | 三文鱼双虾至尊月堡 | 3 | — |
| 小食 | 小杯玉米杯 | 3 | −¥1.50 |
| 饮料 | 锡兰红茶 | 3 | +¥4.50 |

用户问：**"方案一的表格是不是没把BFF四宫格加进去"** —— 是的，漏了。

### 根因

表格是**按「选配轮次」组织的**。BFF 四宫格不属于任何一轮，它是加购项，
于是**没有位置可放，被漏在表外**。但总价里已经算了它的 ¥39.80。

结果：把表里的数加起来，怎么都到不了 ¥153.50，**表失去了核对功能**。

### 为什么这比算错更麻烦

- 算错至少数字是错的，用户一问就能发现
- 漏项时**总价是对的**，只是表加不出来 → 用户会怀疑是不是又算错了，得来回问两轮
- 商务场景尤其致命：三个人在场，客户看表加不出总数

### 解法（已落地）

1. 铁律 22 补一条：混合方案必须逐项列全，**明细小计之和 = 总价**
2. 「套餐标注与选配建议」加「混合方案怎么列」小节，给出正确排版
3. 自查动作写死：**把「小计」列竖着加起来，必须等于「合计」**

正确排版要把加购项单独列一行：

| 组成 | 数量 | 小计 |
|---|---|---|
| 套餐 ×3 | 3 | ¥110.70 |
| └ 小食换玉米杯 | 3 | −¥1.50 |
| └ 饮料换红茶 | 3 | +¥4.50 |
| **加购 BFF四宫格** | 1 | **¥39.80** |
| **合计** | | **¥153.50** |

### 教训

> **表格的用途是让人核对，不是让人看。**
> 任何进了总价却没进表的项，都是在给用户制造一次"我是不是算错了"的自我怀疑。

## 26. ❌ 用 HTML 表格加背景色，聊天里直接变成源码（2026-10-24 用户反馈）

### 现象

用户要求"给套餐部分加颜色背景"。我判断 Markdown 表格不支持 `background`，
于是改用 HTML `<table>` + 行内 `rgba()` 背景：

```
<tr style="background:rgba(255,193,7,.22)"><td>...</td></tr>
```

数据全是真算的，配色逻辑也讲得头头是道。用户回复：**"表格未成功渲染"**。

### 根因

**聊天渲染器不解析内联 HTML 块**，整段 `<table>` 被当纯文本转义输出。
我按"标准 Markdown 支持内联 HTML"的通用假设做设计，但**实际渲染器是受限的**。

更糟的是：这类失败**不会报错**。我这边生成的是合法 HTML，看起来完全正常，
只有到了用户屏幕上才知道渲染不了。

### 判断链条错在哪

| 环节 | 我的判断 | 实际 |
|---|---|---|
| Markdown 表格能设背景色吗 | 不能 | 对 |
| 那用 HTML table 行不行 | 能，Markdown 支持内联 HTML | **错 —— 这个渲染器不支持** |
| 不支持的后果 | 退化显示 | **整段变源码** |

我跳过了"这个渲染器到底支持什么"，直接假设了通用的 Markdown 规范。

### 解法（已落地）

改成**纯 Markdown + emoji 语义色块**，一定能渲染：

| 行类型 | 标记 |
|---|---|
| 套餐主行 | 首列 `🟨` + 名称加粗 |
| 套餐子项 | 全角空格缩进，不加 emoji、不加横线 |
| 单点行 | 首列 `⬜` |
| 合计行 | 加粗，不加 emoji |

**为什么这个方案够用**：🟨 一出现，下面缩进的行自动被视觉归入同一个套餐；
⬜ 顶格出现，说明是另外点的；全单点方案里没有 🟨，颜色本身就说明了"这单没有套餐"。

### 教训

> **关键呈现用"一定渲染"的语法，不要用"规范支持但渲染器未必实现"的语法。**
> 背景色是锦上添花，但如果它把整张表变成源码，就是把主食弄没了。

**判断可信度**：HTML 表格在浏览器里 100% 好用，在聊天里是否好用取决于渲染器。
凡是依赖"渲染器行为"的方案，都要先想到降级。
